## Часть 2: порядок работы

M10 — протокол проверки в игре. Делать первой. Пока ни один отредактированный сейв не загружался в игре, любая запись — предположение. Процедура: копия сохранения, правка одного значения (деньги), загрузка в игре, проверка что значение совпало, повторное сохранение в игре и разбор получившегося файла своим парсером. Последний шаг обязателен: если игра загрузила наш файл, но при пересохранении выдала структуру, которую парсер больше не понимает, значит мы собрали формально валидное, но чужое движку. Результат для каждой игры записать в docs/evidence/INGAME_VERIFICATION.md. Прошло — возможность включается, не прошло — остаётся выключенной с записанной причиной. Не переносить результат одной игры на три: версии движка разные.

M11 — каталоги. Предметы уже читаются из ресурсов установленной игры, и по ним видно, что данные у игр разные: 389 / 417 / 434 записи, общих 261. Добавить группировки и нужные для правок идентификаторы, читая их оттуда же. Ни одного списка предметов, группировок или идентификаторов, вписанного в код руками: в Чистом Небе есть сама Чистое Небо и ренегаты, в Зове Припяти зомбированные, состав не совпадает, и зашитый список через полгода станет враньём, которое выглядит как факт.

M12 — ремонт: прочность оружия и брони, в слотах и в инвентаре, это два разных места хранения и оба обязательны. Порядок сериализации брать из исходников X-Ray, а не угадывать: ixray-1.0-stsoc, ixray-1.5-stcs, ixray-1.6-stcop, OpenXRay xray-16. Диапазон значения и его смысл определить по исходникам и подтвердить на корпусе: у изношенного и нового предмета значения обязаны отличаться предсказуемо.

M13 — предметы: добавить из каталога игры, удалить, изменить количество. Отдельно проверить: количество патронов живёт в двух местах состояния объекта и менять надо согласованно; добавление не должно приводить к состоянию перегруза, из которого игрок не выйдет; удаление квестового предмета может сломать сюжетную цепочку и относится к уровню «опасно».

M14 — отношения с группировками: отношение группировок к игроку и, где формат это хранит, между собой. Реестр отношений сообществ и актёра, диапазоны и пороги враждебности — из исходников. В Чистом Небе система войны группировок богаче, её состав нельзя переносить с Зова Припяти.

M15 — принадлежность игрока к группировке. Главная сложность: игра сама решает, кем игрок может быть и когда. Пример владельца: Шрам в Чистом Небе не может оказаться в Долге, пока не пройдена соответствующая миссия, до этого сюжетный скрипт перепишет значение обратно. Таких случаев много и они разные в трёх играх. Исследовать, где хранится сообщество актёра, какие значения игра считает допустимыми, и в каких известных случаях сюжет перезаписывает выставленное вручную.

M16 — запись в папку игры с резервной копией и восстановлением, для десктопа. Порядок: резервная копия с проверяемым хэшем, запись во временный файл рядом, атомарная замена, перечитывание и сверка. Восстановление возвращает слот в исходное состояние одним действием. Механизм журнала резервных копий уже есть для S.T.A.L.K.E.R. 2, распространить на трилогию. Замена в папке игры — явное действие, а не поведение по умолчанию.

## Часть 3: решение по опасным правкам

Владелец задал вопрос: блокировать правки, которые игра сама ограничивает, или предупреждать? Решение принято: **предупреждать, никогда не блокировать молча.**

Причины: редактор не знает состояние квестов, и чтобы надёжно блокировать, пришлось бы моделировать сюжетную логику трёх игр — это отдельный проект, и он всё равно будет ошибаться. Запрет ударит по легитимным случаям: игрок, который миссию уже прошёл, получит отказ без причины. И врать «нельзя», когда на самом деле «мы не знаем», — ровно то, чего проект избегает во всём остальном.

Три уровня, видимые в интерфейсе:

Безопасно — значение само по себе: деньги, количество, прочность. Обычная правка.

С риском — влияет на поведение мира: отношения с группировками. Пометка в списке изменений.

Опасно — может рассинхронизировать сюжет: принадлежность игрока, удаление квестовых предметов. Явное предупреждение с текстом, что именно может сломаться, и обязательная резервная копия до записи.

Где ограничение игры известно — писать конкретно. «Чистое Небо: смена группировки до соответствующей миссии обычно перезаписывается сюжетным скриптом» полезнее, чем «будьте осторожны». Общая фраза не годится.

## Жёсткие правила

- Одна карточка = одна ветка = один PR. Заголовок и описание PR обязаны соответствовать содержимому: если в PR парсер, в описании не может быть написано «парсер не добавлялся».
- Сначала тест, который падает по той причине, ради которой карточка заведена, с приложенным выводом. Потом минимальная реализация. Потом make check и make test, оба зелёные, и все четыре job в CI.
- Возможность включается в FormatCapabilities только после проверки загрузкой в игре по процедуре M10. Не раньше и не «похоже, работает».
- Никаких зашитых в код списков предметов, группировок и идентификаторов: только чтение из ресурсов установленной игры.
- Не угадывать смещения и порядок полей: движок X-Ray открыт, порядок сериализации берётся из исходников.
- Не переносить результат одной игры на другую: версии spawn 118 / 124 / 128 различаются.
- Побайтовая пересборка без изменений остаётся обязательной для всех форматов.
- Не писать в папку игры без резервной копии, которую можно восстановить.
- Не блокировать правку под видом знания сюжета; предупреждать конкретно.
- Не трогать и не коммитить личные сейвы владельца: в репозиторий идут только хэши, смещения и выводы.
- Логика, общая для интерфейсов, живёт в editor/, а не в ui/, иначе не попадёт в браузерную сборку.
